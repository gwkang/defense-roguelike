# Execution supervision

Apply [bounded artifact verification](../../game-task-planning/references/verification-scope.md) to each selected output. Freeze its criteria and repair scope before dispatch; carry the same contract into every retry and UI handoff. Out-of-scope findings are deferred observations, never automatic tasks or new gates.

## Preparation and ownership
Use the run template; the overall supervisor alone edits the shared record. Workers return results using its result envelope. Resolve request intent before executing. Require a template and rules for each selected output: reuse the producing skill's existing format; if absent, have its owner define a scoped format and content checks before production. Do not label all bundle outputs standardized merely because this envelope exists.

For a small workflow supervise directly. Introduce a part supervisor only for a useful independent group with clear input/output and internal coordination. Default to overall plus one part level; count actual supervisors against available slots. Programming supervision watches interfaces, state ownership and integration risk; UI supervision watches selected references, coverage and asset/runtime readiness. Neither can overrule specialist verdicts or alter another part's scope. Refer cross-part conflicts to overall supervision and technical/product owners.

## Structural design escalation
Before implementation, ask the planner whether the selected slice can preserve the current responsibility, state-owner, interface and lifecycle contracts. Require `game-technical-design` when evidence says the slice will make a consequential change to any of them, when an exception would bypass an ordinary readiness boundary by creating maintained product structure, or when provisional code may become a shared baseline. A large file, unfamiliar pattern or aesthetic preference alone is not a trigger; record the concrete consumer, invariant or ownership risk.

The supervisor may define the problem, authority and blocked consumers, but does not choose the architecture. The design owner returns the current decision revision, allowed implementation boundary, affected consumers and observable checks. Planning then assigns the specialist implementers. If the design is unresolved, continue only work independent of that decision.

Treat bootstrap and provisional implementations as temporary contracts, not implicit architecture approval. Record their owner, permitted consumers, forbidden expansion, replacement or promotion criteria and the downstream task that closes the provisional state. Do not promote them to a maintained baseline merely because focused tests pass. If repeated defects reveal distinct responsibility or ownership failures in the same boundary, stop local repair expansion and route a bounded design review; this does not authorize refactoring before that review.

## Task slices and context handoff

For gameplay development, require the planner's recorded code-impact decision before scheduling final visual polish after the playable slice. Accept a deferrable verdict only against selected design or explicit structural constraints; when neither exists, keep the verdict unresolved and settle the affected structure without requiring full visual polish. When structure is likely to change substantially, settle only the affected player-flow, input, state, responsive or component boundary early; when impact is unknown under known constraints, commission one bounded representative target-runtime probe and decide from it. For a deferrable polish, prioritize agreed rules and interactions, a minimal interface in the actual target runtime, and an end-to-end player-loop check. Formal style, mockup, catalog and asset readiness remain gates for final UI integration and acceptance, not for that functional slice. At each join compare the actual UI code impact with the deferral decision; if it becomes substantial, stop the late-polish branch and replan affected implementation. Report functional and visual readiness separately, and after polish reopen only functional criteria affected by changed behavior, hit geometry, state meaning or dependencies.

Before dispatch, turn the next ready branch into the smallest slice with one observable result, one accountable owner, a known consumer and an acceptance check. Split when ownership, write/resource boundaries, prerequisite decisions or independently observable results differ; combine compatible tiny changes when separation would add only handoff documents. Do not select a role or artifact merely because it exists in the bundle. Estimate an appropriate time/token/attempt budget for the slice and the whole run; at each return compare actual progress with that budget. Progress means a changed candidate, resolved decision or new evidence that can change the next action, not another restatement of the same plan.

For expensive UI capture or renderer work, place a bounded contract/environment preflight before formal production. The preflight may lint locks and run a non-retained representative smoke capture, but it cannot satisfy mandatory coverage or approval. If it fails, route the smallest blocker to the contract owner or test infrastructure and do not consume formal repair attempts on an environment failure. Once it passes, prefer one batched formal run over per-image process launches when the tool supports batching, and record the preflight result and remaining time budget in the checkpoint.

Keep the run template's current checkpoint concise and authoritative for resumption: goal/authority, selected slice and candidate identity, environment/reference roles, current verdict and evidence locators, active owners, one leading blocker/next action, and remaining budgets. The event log remains history, not the default resumption input. Refresh the checkpoint at dispatch, return, repair, scope change and before context compaction. On resume, read it and only the linked current inputs, then check actual files, worker status and input identities before acting. An absent or stale checkpoint requires reconciliation, not replaying or trusting the entire transcript.

For authority reconciliation, compare the checkpoint's authority cursor with explicit user instructions and decisions/events created after it. Preserve earlier skip/defer decisions as history, but let a later explicit resume supersede only the named branch. Before the next affected mutation dispatch, record the superseding authority, resumed branches, still-deferred branches and new goal revision. If current work or candidate identity has advanced beyond the shared record, use `needs-reconciliation` and block only new affected mutation dispatches until the checkpoint catches up; do not label the work unauthorized solely because the checkpoint is older.

Keep a checkpoint revision or last-incorporated event ID and a candidate digest sufficient to detect drift. A changed candidate during an owned implementation or repair is normal execution, but evidence for the previous identity becomes stale for affected criteria until the new candidate is frozen and rechecked. Do not turn ordinary in-flight candidate movement into a separate defect.

Give each worker a bounded dispatch brief: one result, acceptance IDs, exact input/decision locators and revisions, reference versus target runtime, read/write/resource boundary, exclusions, check and return location, budget and stop condition. Use only the minimum relevant conversation context. Workers return the result envelope; before their own context compaction or a handoff, they return a short interim checkpoint with consumed revisions, candidate/changed paths, completed checks, unresolved blocker and next action. Interim records never count as completed evidence. The supervisor verifies current identities before reuse and merges only the essential state into the overall checkpoint. Do not copy the full run history into worker prompts.

Parallelize only slices whose inputs, write paths, verification reads and exclusive resources do not conflict; otherwise serialize. Keep one owner of each shared artifact and one overall supervisor. An independent verifier may check a compatible batch on a stable candidate while recording separate verdicts. A part supervisor is justified by genuine independent coordination, not by context length alone.

## Questions and part reassignment
Specialists return observations, decision sources, recommended options and blocked criteria internally. The overall supervisor resolves existing/delegated choices and sends only remaining material questions together; direct specialist calls follow the common question route.

Use the run template's supervisor assignment table. To add/remove/reassign a part: identify affected tasks and current owner → stop dispatch for those tasks → confirm active affected workers stopped → record new plan revision, task/read/write/resource boundary and shared remaining retry budget → retire the old assignment → activate the new assignment once. If stop/ownership is uncertain, block affected dispatch. Transfer result locators; retain results only when input/criterion revisions and independence remain valid. Preserve independent branches. Adding a supervisor never resets retry counts or changes product scope. This is a single-writer procedure, not atomic ownership or crash recovery.

For UI decisions apply [the UI adapter](../../game-task-planning/references/ui-adapter.md); delegate selection and actual PO approval are distinct records.

For formal UI dispatch, read the planner's `UX prerequisite` and compare its exact decision/reuse scope with the current screen content, target, input and interaction. An absent, unverified, unresolved or stale prerequisite makes affected formal design/production consumers not ready; dispatch the UX owner first and keep the blocking task IDs in the checkpoint. At join, repeat this identity and compatibility check before accepting a formal mockup or handoff. Historic technical/fidelity PASS remains historic evidence, not retroactive UX approval. This check does not block exploratory draft or the separately contracted playable functional interface.

## Readiness and result acceptance
A task is ready only if selected, predecessors' required results passed, current required inputs exist and are semantically usable, material decisions are settled/delegated-and-decided, authority/tools exist, resources are available and no active attempt owns the scope. A skipped branch needs a reason and must not hide an unmet requirement.

For a code-native/native-widget `ASSET_NOT_REQUIRED` binding that needs target-size source parity, plan the [UI implementation source-preparation mode](../../game-ui-implementation/SKILL.md) as a distinct candidate after the approved catalog and `READY` handoff row, before asset-packet readiness. Asset production verifies that source/render; only then can the normal full-integration task depend on binding and packet `READY_FOR_IMPLEMENTATION`. Preparation cannot satisfy that full-integration predecessor by itself.

Source preparation is never a workaround for missing product architecture or screen implementation readiness. If producing parity evidence would require a product screen, entry controller, live binding, navigation or shared runtime state, return the dependency to planning and the appropriate design or implementation owner instead of broadening the preparation slice.

Before a dispatch record its ID and attempt, actual skill path, input revisions, write/read scopes, resources and result location. When the tool supports model overrides, resolve and record the task's capability tier using [model routing](model-routing.md); otherwise retain `host-default` with the fallback reason. After spawning record the actual executor ID and acknowledged model when available. Missing creation acknowledgement means uncertain dispatch, not permission to spawn a duplicate. Inspect available host state or block/isolate the affected scope. This Markdown procedure is not atomic dispatch.

On return inspect artifacts and observations, not only prose. Compare the deliverable with its actual producing skill/template, including incidental setup documents. Installation, link, schema or hash checks prove only those properties; they cannot establish content completeness or usability. Report incomplete content as draft/unverified with the missing applicable criteria, even when setup checks passed. Match run/task/attempt and consumed revisions. Record execution state separately from verdict: a verifier can complete its checks and return fail. Reject late or stale results as evidence for the current candidate. Require a result envelope even for failures. Missing content returns to its owner.

Classify audit and status findings by evidence strength. A `confirmed-defect` requires a current observed product or contract failure. A `recording-gap` means authority, candidate or task state is newer than the shared record but does not by itself prove unauthorized work or product failure. An `operational-risk` identifies a plausible future failure without current failure evidence. Report these separately and do not aggregate them as equally confirmed problems.

## Event-driven workflow audit

Use `game-workflow-audit` only for a bounded event where its expected decision value justifies time, tokens and one concurrent-agent slot. Eligible triggers are a repeated same-cause failure lineage, explicit user rejection or correction, lack of meaningful progress against the recorded budget, a consequential multi-skill join, or a pre-completion retrospective. Do not dispatch it automatically for every task, keep it alive between events, or substitute it for product verification and specialist review.

Start in shadow mode. Record the trigger, expected benefit, source/revision set, actual consumed skills and immediately adjacent handoffs, exclusions, budget and stop condition before dispatch. The auditor reads only that path and its current run/dispatch/result/artifact/raw-evidence records; it does not enumerate the full installed skill set. It returns `workflow-audit@1` and makes no writes. Stop the audit when the named sources are inspected, the budget is exhausted, identities cannot be reconciled, or attribution requires new observation.

Keep four finding classes distinct: `confirmed-defect`, `recording-gap`, `operational-risk`, and `efficiency-loss`. For cause attribution, require one leading layer—`product`, `environment-tooling`, `evidence-recording`, `execution-handoff`, or `skill-contract`—with confidence and alternatives. Poor output alone does not establish a skill-contract defect; compare the actual consumed rule to determine whether it was absent or ambiguous, violated during execution, or already sufficient.

A finding is never an automatic task, gate, edit, retry, blocker or expansion of acceptance. The overall supervisor records `observe-only`, routes an already-authorized product/tool/record correction to its owner, or requests the separate authority needed for a workflow change. A limited skill-improvement proposal is eligible only when the owning skill and failing boundary are exact, the current contract cannot adequately prevent or detect the problem, and one severe evidenced failure or a repeated same-cause lineage warrants the added burden. Freeze the minimum rule change, exclusions, original-case check, unrelated compatible burden/regression check, expected benefit, cost and rollback signal.

The auditor must not author the proposed change. A separately authorized skill author edits only the frozen scope. A verifier different from both auditor and author checks original-case detection and unrelated-case burden before the supervisor accepts the change. Static validation and forward walkthroughs do not prove game quality or realized efficiency. Record measured and estimated costs separately.

This mechanism is instruction-driven and non-persistent. It cannot observe private reasoning, recover evidence that was not preserved, provide telemetry, reserve resources atomically or continue after its bounded call. Count its slot cost and prefer no audit when the same decision can be made directly from current evidence.

## Failure, repair and restart
Distinguish product failure, incorrect/missing input, and environment/tool blockage. Route product failure to its implementation/diagnosis owner, expectation ambiguity to specification, harness failure to test infrastructure. Verifiers do not fix product code to pass. Default repair limit is two attempts per underlying failure lineage unless a known project policy supplies another value; record the limit before execution. Assign a lineage ID to the criterion/underlying defect across design, implementation and verification tasks; task-local attempt numbers are ledger views of that one remaining budget. Reassignment, a new task name, artifact or stage does not reset it. A retry requires a changed hypothesis, input or check that could resolve the observed failure. When the same evidence returns without such a change, or the lineage/run budget is exhausted, stop the affected branch and diagnose whether the criterion, environment, dispatch or product is wrong; return the smallest blocker and owner. Continue independent authorized work, but do not manufacture documentary progress.

For a UI repair, record the changed property, its owner, consuming screens/states/targets, and affected criteria/evidence before dispatch. Apply [fast iteration's impact and runtime-evidence rules](../../game-task-planning/references/ui-fast-iteration.md): retain mandatory coverage, recheck affected criteria on the current candidate, and reuse earlier evidence only where its original build identity and independently verified lack of impact are recorded. Unknown impact requires current observation; out-of-scope findings remain deferred observations.

Before reassigning a scope, confirm the old worker stopped. On input changes revise the plan and invalidate affected evidence. Preserve completed independent work. On resumption inspect current files, active workers and input versions before continuing. Never infer termination from silence. Preserve partial writes and user changes; do not blindly reset shared files.

## Integration and completion
Assign an implementation owner for integration code; the supervisor's join is a control operation. Freeze or isolate the assembled candidate before checks. Link every in-scope acceptance criterion to artifacts and current verification; all-success tasks with uncovered criteria are not complete. Run required project gates and independent reviews, plus actual UI acceptance where selected. After repairs rerun affected checks and reviews on the new candidate within the frozen verification contract. Preserve unaffected valid evidence; passing scoped criteria end the loop.

Use the final-report section to distinguish complete, partially complete, blocked and failed, with actual evidence and remaining work. No generic final permission is needed when all authorized work and required decisions are satisfied. Out-of-scope publication stays separate.
