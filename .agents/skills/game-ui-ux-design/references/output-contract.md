# UX decision and handoff contract

Produce one concise **UX design decision** for the assigned screen/flow. Use the common artifact envelope and record the exact input revisions. Keep the decision in the existing run or UI handoff when that is sufficient; do not require a new document for every small revision.

1. **Player task and evidence** — intended player, situation, immediate goal, current obstacles and preserved behavior. Label each consequential statement `confirmed`, `derived`, `proposed`, or `OPEN`, with a source. A hypothetical player viewpoint is a design lens, not user-research evidence.
2. **Task-flow model** — entry, key decision, action, system feedback, completion, cancel/back, error and recovery where applicable. Show how the player knows the current state and the next available action. Do not define new game rules or side effects.
3. **Information and interaction hierarchy** — what must be visible first, what may be secondary or disclosed later, grouping and scan order, action priority, affordances, focus/keyboard or other supported input path, and non-color state cues. Use actual content/action boundaries; do not make a short placeholder the design baseline.
4. **Layout intent** — for materially different states and declared targets, describe the space and density tradeoff, grouping, reachable controls, and growth/scroll/overflow behavior. State the intended steady-state experience separately from transitions. Leave unsupported pixel values and platform assumptions `OPEN`.
5. **Decision and tradeoff** — selected structure and why it serves the task. When materially different structures are plausible and no current approved decision resolves them, compare their effect on comprehension, effort, errors, and target fit; record rejected options briefly. Respect user-retained approval and delegation authority.
6. **Observable UX scenarios and handoff** — a first-use path, the densest sourced content/action path, and a relevant error/recovery or return path when applicable. State what the next author must preserve, which component capabilities are needed, what screen-spec must make exact, and what remains `OPEN`/`BLOCKED` with the correct owner.

Before returning, walk each scenario against the proposed structure and actual content. If an essential action, explanation, status or recovery is hidden or ambiguous, change the UX decision within scope before handing it to visual production. A walkthrough is design reasoning, not measured usability, runtime validation or user approval. A separate verifier checks that the decision is source-backed, internally coherent, covers the assigned scenarios, and does not trespass on product, art, component or screen-spec authority.

Keep a new or changed UX decision `DRAFT` until its consequential choices are resolved under the shared UI decision rules. Only a resolved decision with exact identity/revision, or a documented compatible approved reuse, may support formal component, screen-spec, or mockup work. Unresolved product choices block only dependent formal work; they do not prevent an explicitly provisional exploratory draft.
